# Глава 8. Зачем процессорам нужен блок выборки инструкций (Instruction Fetch Unit)

В пятой главе мы постигли, как предсказатель переходов (branch predictor) гадает, куда именно направить стопы исполнения дальше. В шестой главе нам открылась суть Очереди Целей Выборки (Fetch Target Queue, FTQ) — сумеречной зоны, где буферизируются эти прозрения, управляется спекулятивная реальность и вершится координация восстановления после неизбежных ошибок. Седьмая глава поведала, как кэш инструкций хранит и выдает во внешний мир байты инструкций. Но байты — это еще не инструкции. Кэш инструкций, подобно равнодушному демиургу, возвращает сырой, нерасчлененный блок памяти — скажем, 64 байта — и где-то в недрах этого монолита таится переменное число инструкций переменной длины. Что еще хуже, в отношении некоторых из них предсказатель переходов вполне мог жестоко ошибиться, вступив на ложный путь. Бэкенд на стадии декодирования, будучи существом строгим и педантичным, ожидает кристально чистого, упорядоченного потока отдельных записей инструкций, каждая из которых наделена собственным программным счетчиком (PC), флагом валидности и метаданными предсказания переходов.

Должно быть нечто, способное перекинуть мост над этой зияющей бездной. Это нечто — **Блок выборки инструкций (Instruction Fetch Unit, IFU)**.

### ASCII Ментальная Модель (Прочти это в первую очередь)

```text
Без IFU:                                     С IFU:

 ICache                  Decode               ICache           IFU              Decode
 ┌──────────────────┐   ┌──────────┐          ┌────────────┐  ┌────────────┐  ┌──────────┐
 │ 64 сырых байта   │──>│ ???      │          │ 64 сырых   │─>│ детекция   │─>│ чистые   │
 │ (смесь 16b/32b)  │   │ где      │          │ байта      │  │ границ     │  │ записи   │
 │ (пол-инструкции  │   │ начало   │          │            │  │ уплотнение │  │ инструк. │
 │  в конце блока)  │   │ инструк- │          │            │  │ выравниван.│  │ с PC     │
 │ (байты ложного   │   │ ций?     │          │            │  │ верификац. │  │ и флагами│
 │  пути примешаны) │   │ какие    │          │            │  │ предсказан.│  │ валидн.  │
 │                  │   │ валидны? │          │            │  │ RVC расш-е │  │          │
 └──────────────────┘   └──────────┘          └────────────┘  └────────────┘  └──────────┘
                                                                    │
 Результат: замешательство при                      Редирект ──────>│ FTQ
 декодировании, впустую потраченные                 (при ошибке     │
 такты, загрязнение ложным путем                    предсказания)
```

**IFU трансформирует сырые, варьирующиеся по длине, спекулятивно извлеченные байты в точный, выровненный, верифицированный поток инструкций, который бэкенд способен поглощать с максимальной пропускной способностью.**

## 8.1 Проблема сырых байтов

### 8.1.1 Что идет не так без IFU

Представьте себе, что мы соединили кэш инструкций напрямую со стадией декодирования. Кэш доставляет 64-байтный монолит сырой памяти. Для того чтобы извлечь смысл из этого хаоса, декодеру нужно знать три вещи о каждой инструкции: где она начинается, какова её длина и находится ли она на правильном (истинном) пути исполнения. Если нет специальной логики, которая ответит на эти вопросы, немедленно возникают три экзистенциальные проблемы.

**Проблема 1: Инструкции переменной длины.**
Архитектура RISC-V с установленным расширением (RVC) беспечно смешивает 16-битные и 32-битные инструкции в рамках одного блока выборки. 64-байтный блок может содержать от 16 инструкций (все 32-битные) до 32 инструкций (все 16-битные), либо любую их комбинацию. Декодер не может просто нарезать этот блок на равные слоты фиксированной длины — он обязан вычислять начало каждой следующей инструкции, напряженно вглядываясь в младшие биты каждого полуслова. Инструкция, чьи два младших бита равны `11`, имеет ширину 32 бита; в противном случае — 16 бит. Этот процесс сканирования по своей природе сугубо последователен: знание того, где начнется инструкция N+1, зависит от того, какова длина инструкции N.

**Проблема 2: Инструкции, раскинувшиеся по обе стороны границы блоков.**
32-битная инструкция может лежать одной ногой в блоке А, а другой — в следующем за ним блоке В. Последние два байта блока А содержат её первую половину, а первые два байта блока B — вторую. Если не переносить состояние сквозь циклы выборки, эта инструкция бесследно сгинет в небытии — она предстанет в виде двух искаженных, невалидных фрагментов по обе стороны разлома.

**Проблема 3: Примесь байтов ложного пути.**
Блок был запрошен, повинуясь воле предсказателя переходов. Если предсказатель сказал "переход совершен (taken) на смещении в 20 байт", то лишь первые 20 байт таят в себе что-то полезное. Оставшиеся 44 байта находятся за горизонтом предсказанного изменения потока управления и вообще не должны подвергаться декодированию. Не имея механизма маскировки или усечения, декодер в слепой ярости попытается переварить этот информационный мусор, порождая фантомные исключения или портя состояние конвейера.

### 8.1.2 Оценка стоимости потерь

Каждая из этих проблем, будучи проигнорированной, наносит ощутимый, измеримый урон производительности:

- **Ошибки на границах** заставляют декодер неверно истолковать инструкцию, что вызывает исключение неверной инструкции или тихо, как яд, порождает неправильный код операции. Восстановление требует полного сброса конвейера (flush) — что для глубокой out-of-order машины обычно стоит 10–20 тактов.

- **Потерянные на границах блоков инструкции** означают, что при каждой выборке, пересекающей границу, одна инструкция никогда не будет исполнена. В коде, густо насыщенном RVC (что является обычным делом, ведь компиляторы обожают генерировать сжатые инструкции), примерно 1 из 16 блоков выборки оканчивается обрубком полуинструкции. На частоте 1 ГГц при одной выборке за такт это оборачивается ~60 миллионами безвозвратно утерянных инструкций в секунду.

- **Декодирование ложного пути** впустую сжигает пропускную способность декодера и захламляет нижележащие буферы бесполезными записями, создавая обратное давление (backpressure) на фронтенд и задерживая инструкции, идущие по истинному пути. Исследования спекулятивных процессоров показывают, что подобное загрязнение способно снизить эффективный IPC (количество инструкций за такт) на 5–15%, даже при наличии блестящего предсказателя.

## 8.2 Спроектируй это сам: От наивности к реальности

Зная об этих жестких ограничениях, как бы вы сами спроектировали логику между кэшем и декодером? Давайте сотворим решение слой за слоем, обнажая каждую причину краха перед тем, как предложить спасительный механизм.

### Слой 1: Нарезка на фиксированную ширину (наивный путь)

Самый прямолинейный подход: считать каждые 32 бита одной инструкцией.

```text
  Блок выборки (64 байта):
  ┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐
  │ W0 │ W1 │ W2 │ W3 │ W4 │ W5 │ W6 │ W7 │ W8 │ W9 │W10 │W11 │W12 │W13 │W14 │W15 │
  └────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘
  Нарезка на 16 фиксированных 32-битных слотов → максимум 16 инструкций
```

**Где все ломается:** С появлением RVC две последовательные 16-битные инструкции спокойно уживаются внутри одного 32-битного слота. При фиксированной нарезке они будут приняты за одну сплошную сущность, теряя половину заложенного смысла. В коде RISC-V с включенным сжатием (`-march` содержит `c`) обычно 40–60% инструкций являются сжатыми. При нарезке фиксированной шириной мы бы потеряли почти половину всего потока инструкций.

### Слой 2: Обнаружение границ

Сканируем блок с гранулярностью в 16 бит. Для каждого полуслова всматриваемся в биты [1:0]: если они оба равны `1`, полуслово представляет собой начало 32-битной инструкции (поглощая это полуслово и следующее за ним); иначе это полноправная 16-битная инструкция.

```text
  Позиции полуслов:     0     1     2     3     4     5     6     7     8
                     ┌───────────┬─────┬───────────┬─────┬─────┬───────────┐
  Размер инструкции: │  32 бита  │ 16б │  32 бита  │ 16б │ 16б │  32 бита  │ ...
                     └───────────┴─────┴───────────┴─────┴─────┴───────────┘
  Вектор начал:         1     0     1     1     0     1     1     1     0
  Вектор концов:        0     1     1     0     1     1     1     0     1
```

Так рождается *вектор валидности инструкций* (указывающий, какие позиции полуслов являются началом инструкции) и *вектор конца инструкций* (какие позиции являются концом). Вместе они определяют контуры каждой инструкции в блоке.

**Где все ломается:** Обратим взор на последнее полуслово блока. Если это первая половина 32-битной инструкции, её вторая половина пребывает в *следующем* блоке выборки. Обнаружение границ внутри одного, изолированного блока не может заглянуть за горизонт. Такая полуинструкция будет либо отмечена как невалидная (и потеряна во тьме), либо ошибочно воспринята как 16-битная инструкция.

### Слой 3: Состояние переноса между блоками

Дабы спасти инструкции, пересекающие границы миров, IFU должен помнить состояние предыдущего цикла выборки. В частности, ему надлежит хранить память о том:

- Было ли последнее полуслово предыдущего блока первой половиной 32-битной инструкции (**флаг полуинструкции**).
- Если да, то каковы были фактические данные этого полуслова (**данные полуинструкции**), которые должны слиться с первым полусловом текущего блока, дабы переродиться в полноценную 32-битную инструкцию.

```text
  Цикл выборки T:
  ┌──────┬──────┬──────┬──────┐
  │ ...  │ H29  │ H30  │ H31  │  <-- H31: первая половина 32-битной инструкции
  └──────┴──────┴──────┴──────┘

  Состояние IFU между тактами: [ prevHalf = true, prevHalfData = H31 ]

  Цикл выборки T+1:
  ┌──────┬──────┬──────┬──────┐
  │  H0  │  H1  │  H2  │ ...  │  <-- H0: вторая половина той же инструкции
  └──────┴──────┴──────┴──────┘
     │                    
     └─> Склейка: instr_0 = {H0, H31} (полноценная 32-битная инструкция)
```

**Где все ломается:** В эффективности использования пропускной способности конвейера. Теперь мы умеем склеивать и находить все инструкции, но в самом блоке они распределены неравномерно («размазаны» по 32 слотам полуслов из-за чередования 16- и 32-битных размеров). Более того, если предсказатель заявляет, что переход случился где-то внутри блока, то всё, что находится после него — это мусор с ложного пути, который нужно игнорировать.
В итоге мы получаем «дырявый» массив, где валидные инструкции перемежаются зияющими пустотами. Если попытаться отправить этот массив напрямую потребителю фиксированной ширины (например, в 4-полосный Декодер), мы впустую растратим ресурсы, заставляя его такты обрабатывать воздух.

### Слой 4: Уплотнение и выравнивание

**Уплотнение (Compaction)** решает проблему «дырявого массива». Оно берет прерывистую цепочку разрозненных валидных инструкций и, словно архиватор, сжимает их в единый, монолитный и плотный строй. Если в оригинальном блоке инструкции ютились на позициях {1, 2, 4, 5, 6, 8, 10, 11, 12}, уплотнение лишает их старых координат и присваивает новые, строго последовательные выходные слоты: {0, 1, 2, 3, 4, 5, 6, 7, 8}.

**Выравнивание (Alignment)** вступает в игру следом. Этот плотный строй из 9 инструкций нужно аккуратно уложить в следующий буфер (IBuffer), который разбит на банки. Буфер не всегда готов принимать данные с нулевого слота — его указатель записи (write pointer) может стоять, скажем, на банке №2. Схема выравнивания берет уплотненный строй и "прокручивает" (сдвигает) его по кругу так, чтобы нулевая инструкция легла ровно во второй банк буфера. Это гарантирует, что ни один банк не будет простаивать без дела.

```text
  ┌────────────────────────────────────────────────────────┐
  │ Сырые слоты из детектора:                              │
  │ [   ] [ I0] [ I1] [   ] [ I2] [ I3] [ I4] [   ] [ I5]  │
  └────────────────────────────────────────────────────────┘
                              ▼ Уплотнение (сброс пустот)
  ┌────────────────────────────────────────────────────────┐
  │ Плотный массив:                                        │
  │ [ I0] [ I1] [ I2] [ I3] [ I4] [ I5] [   ] [   ] [   ]  │
  └────────────────────────────────────────────────────────┘
                              ▼ Выравнивание (сдвиг +2 для IBuffer)
  ┌────────────────────────────────────────────────────────┐
  │ Итоговая запись в буфер:                               │
  │ [ I4] [ I5] [ I0] [ I1] [ I2] [ I3] [   ] [   ] [   ]  │
  └────────────────────────────────────────────────────────┘
    Bank0 Bank1 Bank2 Bank3 Bank4 Bank5 Bank6 Bank7 Bank8
```

**Где все ломается:** Теперь поток инструкций девственно чист и плотен, но опирается он всецело на слепую веру предсказателя переходов в то, какие инструкции являются истинным путем. Если предсказатель предрек переход в неверной позиции — или напророчил переход там, где инструкции перехода вообще нет — IFU начнет скармливать бэкенду иллюзии ложного пути. Бэкенд в конце концов осознает обман, но к тому моменту он успеет раскодировать и запустить десятки бессмысленных фантомов.

### Слой 5: Ранняя верификация предсказания

Последний, пятый слой — это внедрение **чекера предсказаний**, инспектора внутри самого IFU. После того как детектор границ очертит контуры инструкций, легковесный предварительный декодер производит их первичную классификацию: перед нами условный переход (branch)? Безусловный (jump)? Возврат из функции? Инспектор берет эту природу инструкции и сверяет ее с заверениями предсказателя:

- Заявил ли предсказатель о "переходе" (taken) на инструкции, которая вообще не влияет на поток управления (NotCFI)?
  → **Ошибка NotCFI**: предсказатель бредит; единственно верный путь — продолжать последовательно.
- Предсказал ли он переход для инструкции JAL, но вот беда — вычисленная нами цель не совпадает с предсказанной? → **Ошибка Target fault**: предсказатель опирался на ветхие или фантомные (aliased) данные.
- Упустил ли предсказатель очевидный переход без условий? → **Ошибка InvalidTaken**: предсказатель проглядел переход, который, согласно пред-декодированию, является безусловным прыжком (например, JAL).

Как только инспектор распознает сбой, он немедленно формирует **редирект** обратно в Очередь Целей Выборки (FTQ), выпрямляя поток вычислений еще *до* того, как этот морок достигнет бэкенда. Благодаря этому окно ложного пути сужается с потенциальных десятков тактов (пока бэкенд не закончит выполнение) до краткого мига в несколько тактов (глубина конвейера IFU).

В этом и заключается совершенный архитектон IFU: пять слоев, каждый из которых врачует определенный недуг предыдущего слоя.

> *Глава 8a описывает, как Kunminghu реализует каждый из этих слоев в RTL, включая конкретные стадии конвейера и подмодули.*

## 8.3 Аналогия с конвейером контроля качества

Вообразите IFU как конвейер контроля качества, пролегающий между складом (кэшем инструкций) и сборочной линией (стадией декодирования).

```text
  Склад                 Конвейер контроля качества                    Сборочная линия
  (ICache)              (IFU)                                         (Decode/IBuffer)
  ┌──────────┐   ┌──────────────────────────────────────────┐   ┌──────────────┐
  │          │   │  ┌──────┐  ┌──────┐  ┌───────┐  ┌──────┐ │   │ Готовые к    │
  │ Сырые    │──>│  │Сорти-│─>│Упако-│─>│Провер-│─>│Марки-│ │──>│ использованию│
  │ ящики    │   │  │ровка │  │вка   │  │ка     │  │ровка │ │   │ детали       │
  │          │   │  └──────┘  └──────┘  └───────┘  └──────┘ │   │              │
  └──────────┘   └──────────────────────────────────────────┘   └──────────────┘
                  Станция 1  Станция 2 Стация 3 Станция 4
                  (детекция  (уплотн-е (проверка (расшир-е
                   границ)    +выравн.) предсказ.) RVC)
```

- **Станция 1 (Сортировка):** Инспекторы вскрывают каждый ящик (полуслово) и решают, цельная ли это деталь (16-битная инструкция) или лишь осколок чего-то большего (первая/вторая половина 32-битной инструкции). Заодно проверяют, не осталась ли частичная деталь от предыдущей партии (перенос полуинструкции).

- **Станция 2 (Упаковка):** Детали плотно утрамбовываются в стандартные лотки (уплотненные слоты) без единого зазора, а затем проворачиваются так, чтобы точно совпасть с текущей позицией приема на сборочной линии.

- **Станция 3 (Проверка качества):** Каждую деталь выборочно сверяют с транспортным манифестом (предсказанием переходов). Если манифест гласит "это цель перехода", а деталь оказывается обыкновенным болтом (не-переход), инспектор поднимает тревогу и отправляет уведомление об ошибке обратно в экспедицию (редирект в FTQ).

- **Станция 4 (Маркировка):** Сжатые детали (инструкции RVC) разворачиваются до своих полноразмерных эквивалентов, чтобы на сборочной линии царило единообразие форматов.

**Где аналогия дает трещину:** Реальный промышленный конвейер не способен на спекулятивную перемотку времени. Когда инспектор IFU обнаруживает ложь в предсказании, он не просто отбраковывает деталь — он посылает сигнал, заставляющий весь фронтенд отмотать время назад и переродиться на другом адресе. У этого механизма спекулятивной реинкарнации нет аналогов в грубом физическом мире простых конвейеров.

## 8.4 Обнаружение границ инструкций в условиях переменной длины кодирования

### 8.4.1 Краткое напоминание о расширении сжатия (RVC) в RISC-V

C-расширение архитектуры RISC-V узаконивает существование 16-битных сжатых инструкций наравне с классическими 32-битными. Правило кодирования пугающе просто: если биты [1:0] полуслова оба равны `1` (то есть значение равно `11` в двоичном виде), инструкция объявляется 32-битной и алчно поглощает это полуслово плюс следующее за ним. В противном случае мы имеем дело со скромной 16-битной инструкцией, довольствующейся лишь этим полусловом.

```text
  16-битная инструкция (сжатая - RVC)
  ┌────────────────────────┬──────┐
  │     Опкод / Данные     │ !=11 │ (биты [1:0] равны 00, 01 или 10)
  └────────────────────────┴──────┘
  15                           1  0
  └────── 1 полуслово ──────┘

  32-битная инструкция (стандартная)
  ┌─────────────────────────────────────────┬──────┐
  │                 Опкод / Данные          │  11  │ (биты [1:0] строго 11)
  └─────────────────────────────────────────┴──────┘
  31                                           1  0
  └────────────── 2 полуслова ──────────────┘
```

### 8.4.2 Алгоритм сканирования

Получив на вход блок выборки из N полуслов, алгоритм обнаружения границ плетет две битовые паутины:

- **instrValid[0..N-1]**: `1` на каждой позиции полуслова, знаменующей *начало* валидной инструкции.
- **instrEnd[0..N-1]**: `1` на каждой позиции полуслова, являющейся *последним полусловом* валидной инструкции.

Сканирование — это методичный путь слева направо:

```text
  pos = 0
  while pos < N:
    instrValid[pos] = 1
    if halfword[pos][1:0] == 0b11:   // 32-битная инструкция
      instrEnd[pos+1] = 1
      pos += 2
    else:                            // 16-битная инструкция
      instrEnd[pos] = 1
      pos += 1
```

Последовательная зависимость (каждый шаг упирается в длину предыдущей инструкции) порождает ужас перед неминуемой потерей времени. В 32-словном блоке наивное сканирование превращается в цепочку переносов длиною в 32 тактовых шага — это недопустимая медлительность для однотактовых вычислений на высоких частотах.

### 8.4.3 Разрыв последовательной цепи: Спекулятивно-параллельные вычисления

Ключевое озарение кроется в том, что цепь переноса на каждом шагу имеет бинарный вход: текущее полуслово либо 16-битное (перенос шагает на 1), либо 32-битное (прыгает на 2). Это означает, что вся вторая половина блока имеет лишь две возможные карты границ, в зависимости от того, как завершилась первая половина: чисто (на границе инструкции) или оборвавшись на полуслове 32-битной RVI-инструкции.

Аппаратура безжалостно эксплуатирует этот факт путем **разрубания блока пополам и параллельного расчета обеих половин**:

```text
            [Блок выборки: 32 полуслова]
           /                            \
   Половина 0 (слоты 0..15)          Половина 1 (слоты 16..31)
  ┌────────────────────────┐         ┌────────────────────────┐
  │ Базовый расчет:        │         │ Двойной спекулятивный  │
  │ С учетом реального     │         │ расчет:                │
  │ переноса от прошлого   │         │ ├─ Ветвь А: перенос = 0│
  │ такта                  │         │ └─ Ветвь Б: перенос = 1│
  └──────────┬─────────────┘         └───────────┬────────────┘
             │                                   │
      [Границы 0..15]                            │
             │                                   │
      Выходной перенос ───────────────────> Мультиплексор
      (0 или 1)                                  │
                                          [Границы 16..31]
```

Первая половина вычисляет свою карту границ, опираясь на известный входной перенос (состояние полуинструкции, перешедшее из прошлого блока выборки). Пока идет этот процесс, вторая половина судорожно и спекулятивно вычисляет *сразу две* карты — одну для случая, если первая половина закончилась ровно, другую — на случай, если конец рассек 32-битную инструкцию. Когда исходный перенос из первой половины становится известен, простой мультиплексор делает судьбоносный выбор, отбрасывая химеру и оставляя правильный результат для второй половины.

Это удваивает затраты на логику (две копии логики второй половины), но разрубает критический путь практически надвое — от 32-шаговой цепи к 16-шаговой плюс мультиплексор. Этот прием универсален: с бóльшим количеством расщеплений цепь можно укорачивать и дальше, расплачиваясь за это экспоненциальным ростом спекулятивных копий. Расщепление надвое — практичная золотая середина для типичных размеров блока выборки.

Это классический трюк проектирования схем, именуемый **спекулятивно-параллельным вычислением** (иногда "сумматор с условным переносом" или "carry-select"). Он обитает в сумматорах, приоритетных шифраторах и любой логике с длинной цепью переноса. В контексте IFU — это самая фундаментальная временная оптимизация для детекции границ.

### 8.4.4 Проблема полуинструкции

Когда последнее полуслово извлекаемого блока оказывается первой половиной 32-битной инструкции, сканирование порождает `instrValid[N-1] = 1`, но бессильно выставить `instrEnd[N]`, ибо позиция N за гранью текущего блока. IFU надлежит:

1. Запомнить, что в конце этого блока таится незримая половина.
2. Сохранить плоть её данных (полуслово).
3. При следующем цикле выборки — пришить сохраненное полуслово к первому полуслову нового блока, словно Франкенштейн, сшивающий из фрагментов полноценную 32-битную инструкцию.

Это переносимое состояние ничтожно мало (один флаг и 16 бит данных), но управлять им следует с изяществом хирурга, проводя через все сбросы (flushes) и редиректы конвейера. Если редирект напрочь инвалидирует текущий поток выборки, фантомная полуинструкция должна быть стерта из памяти — иначе следующий блок, явившийся после редиректа, по ошибке попытается слить свое начало с давно умершим видением.

### 8.4.5 Межстраничные исключения и полуинструкции

Загадка полуинструкций имеет еще одно, более тонкое измерение корректности, касающееся **обработки исключений**. 32-битная инструкция, неловко усевшаяся поверх межстраничной границы, держит свои первые два байта на странице A, а вторые два байта — на странице B. Если страница B вдруг лишена валидного мэппинга (или помечена как неисполнимая, no-execute), попытка извлечь блок B порождает исключение ошибки страницы (instruction page fault).

Возникает философский вопрос: какая именно инструкция стала причиной исключения? RISC-V требует точности (precise exceptions) — PC (программный счетчик) виновной инструкции должен быть явлен миру. В данном сценарии виновная инструкция родилась на странице A (ее первая половина успешно скопирована), но само исключение было спровоцировано греховным поползновением к странице B (где ютится её вторая половина).

IFU обязан донести эту тонкую разницу до бэкенда:

1. Отметить печатью исключения *собранную воедино* инструкцию (а не первую инструкцию блока B).
2. Пометить это исключение как **межстраничное (cross-page)**: адрес ошибки находится на следующей странице, но духовный дом инструкции (PC) принадлежит предыдущей.
3. Бэкенд использует этот ярлык, чтобы сымитировать правосудие: CSR-регистр `mepc` (machine exception program counter) устанавливается на PC начала инструкции (на страницу A), в то время как виртуальный адрес сбоя (`mtval`) безжалостно указывает на страницу B.

Не будь этого механизма, процессор либо вообще проморгал бы исключение (приписав вину первой инструкции блока B, которая начинается с совсем другого PC), либо предал бы суду невиновную инструкцию.

### 8.4.6 Разобранный пример: Детекция границ

Возьмем 8-словный блок выборки (упрощено от реального 32-словного ужаса ради человекочитаемости):

```text
  Позиция полуслова:    0       1       2       3       4       5       6       7
                      ┌───────┬───────────────┬───────┬───────┬───────┬───────────────┐
  Данные:             │ x4501 │ x0073 │ x0013 │ x8591 │ x4501 │ x4581 │ x0063 │ x0013 │
  Биты [1:0]:         │  01   │  11   │  xxx  │  01   │  01   │  01   │  11   │  xxx  │
                      ├───────┼───────────────┼───────┼───────┼───────┼───────────────┤
  Архитектура:        │  16b  │      32b      │  16b  │  16b  │  16b  │      32b      │
                      └───────┴───────┴───────┴───────┴───────┴───────┴───────┴───────┘
  instrValid          │   1   │   1       0   │   1   │   1   │   1   │   1       0   │
  instrEnd            │   1   │   0       1   │   1   │   1   │   1   │   0       1   │
```

**Итог сканирования:**
Найдено 6 инструкций (четыре 16-битные, две 32-битные). Позиции `pos=2` и `pos=7` поглощены как вторые половины 32-битных инструкций, поэтому их векторы `instrValid` равны `0`, а `instrEnd` равны `1`.

Если предсказатель переходов провозгласил: "переход на позиции 4", только инструкции на позициях {0, 1, 3, 4} находятся на истинном пути — IFU накладывает маску забвения на позиции 5–7.

## 8.5 Уплотнение и выравнивание: Как эффективно заполнить конвейер

### 8.5.1 Почему редкие позиции тратят пропускную способность

Логика обнаружения границ выявляет инструкции, но оставляет их лежать в массиве на тех же местах, где они были скачаны из памяти. Из-за разной длины инструкций (16 и 32 бита) в этом массиве появляются "дыры" — позиции, которые были поглощены как вторые половины 32-битных инструкций.

Ситуацию усугубляет предсказатель переходов: если он утверждает, что внутри блока произойдет скачок (branch taken), то все инструкции *после* этого скачка объявляются мусором с ложного пути (wrong-path) и отбрасываются.

В результате мы имеем сырой массив (например, шириной в 32 слота полуслов), в котором реальных, валидных инструкций может оказаться всего 4 или 5 штук, хаотично разбросанных среди пустых слотов. 

Если попытаться "влить" такой изрешеченный пустотами массив напрямую в следующую стадию конвейера (Декодер или буфер инструкций), которая имеет фиксированную ширину приема (например, 8 полос за такт), мы столкнемся с катастрофой. Широкие и дорогие полосы приема будут обрабатывать пустые слоты (воздух). Процессор будет тратить такты впустую, работая вхолостую на 50% или 80% своей номинальной мощности.

### 8.5.2 Уплотнение (Compaction)

Уплотнение изживает эти бреши. Оно конвертирует разреженную россыпь валидных позиций в монолитную, непрерывную выходную последовательность:

```text
  Вход (разрежен):    [I0 на pos 0] [_ на pos 1] [I1 на pos 2] [I2 на pos 3] [_ на pos 4]
  Выход (плотен):     [I0] [I1] [I2]
```

Это картографическое чудо совершается приоритетным шифратором (priority encoder) или схемой префиксных сумм (prefix-sum), которая с невозмутимым видом подсчитывает валидные позиции и жалует каждой из них следующий по порядку индекс на выходе.

### 8.5.3 Выравнивание (Alignment)

После уплотнения единый и непрерывный строй инструкций должен быть погружен в нижележащий буфер инструкций (IBuffer). IBuffer организован в виде сонма банков записи, и каждый банк ожидает получить пищу ровно на своей специфической позиции. Если перст указателя записи IBuffer взирает сейчас на банк 2, то первая уплотненная инструкция должна рухнуть в банк 2, вторая — в банк 3, и так далее (делая спираль по возвращении к нулю).

Выравнивание — это банальное вращение (бочечный сдвиг, barrel shift) уплотненного массива на значение текущего указателя записи. Это ритуал гарантирует, что каждый банк будет исчерпывающе использован на каждом такте, вне зависимости от того, какое количество душ-инструкций принес в жертву предыдущий блок выборки.

### 8.5.4 Чувствительность к производительности

От ширины логики уплотнения и выравнивания зависит максимальный темп заглатывания инструкций. Если IFU способен уплотнить от силы K инструкций за такт, а нижележащий буфер обладает B банками записи, общая пропускная способность сковывается цепями min(K, B). Чем больше K, тем тяжелее давление на площадь (шире мультиплексоры) и тайминги (длиннее префиксные цепи). Сделаешь K слишком малым — и узкое горлышко начнет душить поток, когда RVC-тяжелый код набьет множество инструкций в одну выборку.

```text
  Пропускная способность vs. ширина уплотнения:

  Инструкций/такт
       │
   B   │─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  (Лимит записи IBuffer)
       │        ╱─────────────────────
       │      ╱
       │    ╱
       │  ╱
       │╱
       └─────────────────────────────
       0    B/2    B    3B/2   2B
              Ширина уплотнения (K)

  Ниже K = B: Уплотнение есть узкое горло.
  Выше K = B: Пропускная способность записи IBuffer есть узкое горло.
  Расширение K за пределы B принесет лишь потерю площади без навара пропускной способности.
```

## 8.6 Пофрагментное восстановление PC (Program Counter)

### 8.6.1 Проблема: Хранить полный PC для каждой инструкции — чудовищно дорого

Каждая инструкция, отправленная бэкенду, должна нести на своих плечах бремя собственного точного программного счетчика (PC) — бэкенду он нужен как воздух для пересчета целей переходов, отчетов об исключениях и отладки. Наивный архитектор взвалил бы полный виртуальный адрес (состоящий из 39–48 бит) на каждую позицию инструкции в конвейере IFU. Имея в блоке по 32+ слотов, это оборачивается перерасходом в 1200 с лишним бит регистрового состояния чисто ради одних только PC.

### 8.6.2 Озарение: Общие старшие биты

В рамках единого блока выборки все инструкции с братской солидарностью делят одни и те же *старшие* биты адреса. 64-байтный блок простирается не более чем на 64 байта адресного пространства — между инструкциями флуктуируют лишь нижние 6 бит. Даже с учетом ширины выравнивания буфера инструкций, изменяющаяся часть поистине ничтожна.

Путь к оптимизации лежит через **рассечение PC в некой точке отсечения**:

```text
  Полный PC (напр., 39 бит):
  ┌──────────────────────────────┬──────────────┐
  │ Старшие биты (общие на блок) │ Младшие биты │
  │ хранятся ЕДИНОЖДЫ            │ (на инструкс)│
  └──────────────────────────────┴──────────────┘
                                  ^
                            точка отсечения
```

- **Старшие биты** (`pcHigh`): хранятся один раз на вытащенный блок в конвейерном регистре. Вся община инструкций в блоке разделяет это значение.
- **Младшие биты** (`pcLower`): индивидуальны для каждой инструкции. Высчитываются математически как `blockStartOffset + i * 2` (ибо инструкции оседают на выровненных по 2 байта позициях).

### 8.6.3 Проблема переноса

Остается одна червоточина: младшие биты могут переполниться и залезть за точку отсечения. Если точка пролегает на 9-м бите (охватывая 512 байт смещения), а старт блока приходится на смещение 500, причем инструкция таится на 520 байтах, простое сложение младших бит выйдет из берегов. Настоящий PC инструкции — это уже не `pcHigh:520`, а `(pcHigh+1):8`.

Алхимия подсказывает предварительно вычислить `pcHighPlus1 = pcHigh + 1` один раз для всего блока, а затем использовать однобитный сенсор переполнения:

```text
  pcLower = startOffset + instrSlot * 2
  if pcLower переполняется за точку отсечения:
    fullPC = Cat(pcHighPlus1, pcLower[cutPoint-1:0])
  else:
    fullPC = Cat(pcHigh,      pcLower[cutPoint-1:0])
```

Этот изящный трюк подменяет N полновесных сумматоров (по одному на каждый слот) на:
- Единственный полновесный инкремент (для `pcHighPlus1`, вычисляемый единожды за блок).
- N обрезков сложения (для `pcLower`, шириной всего `cutPoint+1` бит).
- N однобитных мультиплексоров (судящих между `pcHigh` и `pcHighPlus1`).

Спасение велико: для 39-битного виртуального адреса с точкой отсечения на 9-м бите каждому слоту нужно хранить лишь жалкие 10 бит вместо 39 — 75-процентное обрезание регистровой ширины.

> *Глава 8a (раздел 8a.3) воспевает параметр `PcCutPoint` процессора Kunminghu и хелпер `catPC`, претворяющий это возрождение в жизнь.*

## 8.7 Ранняя верификация предсказания

### 8.7.1 Популярное заблуждение: "Ошибки предсказания всплывают лишь на стадии исполнения"

> **Популярное заблуждение**
>
> *"Ошибки в предсказании переходов разоблачаются исключительно тогда, когда инструкция перехода наконец-то соизволит исполниться в бэкенде."*
>
> Это правда для условных переходов, чье направление (совершен/не-совершен) завязано на значения в регистрах, недоступные до стадии выполнения. Но существенный пласт ошибок предсказания можно распознать задолго до этого — сразу же, как только инструкции подвергаются предварительному декодированию — потому что они касаются не динамических данных, а *структурных* свойств самого кодирования инструкций.

### 8.7.2 Что способен узреть пред-декодер

После установления границ инструкций IFU проводит их легковесное **предварительное декодирование**. Это не полноценный декод — извлекается лишь тип инструкции (переход, прыжок, возврат, либо вообще не-переход: non-CFI) и, для прямых переходов с прыжками — непосредственное (immediate) смещение. Этой крупицы информации с головой хватит, чтобы вскрыть целые классы фатальных ошибок предсказателя:

| Возможный сбой | Описание | Логика разоблачения |
| --- | --- | --- |
| **NotCFI** | Предсказатель напророчил "переход" на инструкции, которая вообще не является переходом | Пред-декодер клянется, что это не условный переход / прыжок / возврат |
| **JAL target mismatch** | Цель перехода, названная предсказателем, не совпадает с арифметически вычисленной целью (PC + immediate) | Прямое сравнение предсказанной цели с суммой PC и расшифрованного immediate |
| **Invalid taken** | Предсказатель проспал, не отметив ни одну инструкцию как совершающую переход, но пред-декодер находит безусловный прыжок (JAL) | Пред-декодер обнаруживает безусловный прыжок, который предсказатель умудрился не заметить |
| **Return mismatch** | Цель возврата у предсказателя не совпадает с предсказанием стека возвратов (RAS) | Сравнение цели возврата предсказателя с вершиной RAS |

Эти сбои детектируются со 100-процентной гарантией везде и всегда — они не зависят от данных времени исполнения (runtime). Отлавливание их внутри IFU сберегает полновесную глубину конвейера бэкенда, не давая ему расходоваться на призраки ложного пути.

### 8.7.3 Двухступенчатый инспектор

Правоверный чекер предсказаний дробится на две стадии:

1. **Стадия 1 (в том же такте, что и добавление в очередь):** Устанавливает, какие именно инструкции в блоке поражены ошибкой. Сдвигает маску валидности так, чтобы плоды ложного пути даже не коснулись буфера инструкций. Это мгновенно купирует ущерб.
2. **Стадия 2 (такт спустя):** Вычисляет точный адрес (target) редиректа и упаковывает его в послание для FTQ. Этот лишний такт позволяет отнести вычисление целевого адреса в сторону от критического пути записи в буфер.

В расщеплении заложен общий принцип схемотехники: *действуй немедленно на те побочные эффекты, которые в силах проконтролировать локально (маскировка очереди), и бери паузу в один такт для воздействий глобального масштаба (генерация редиректа).*

### 8.7.4 Патологический случай: Вредоносный код, максимизирующий редиректы инспектора

Представьте код, злонамеренно сотканный для того, чтобы довести инспектора IFU до белого каления:

```text
  0x1000:  c.nop        # 16-бит, non-CFI (не-переход)
  0x1002:  c.nop        # 16-бит, non-CFI
  0x1004:  c.nop        # 16-бит, non-CFI
  0x1006:  c.nop        # 16-бит, non-CFI
  ...  (32 подряд идущих инструкции c.nop втиснуты в 64-байтный блок)
```

Если предсказатель (быть может, из-за пагубного наложения адресов в таблицах — aliasing) предрекает "переход" на каждой второй инструкции, инспектор IFU будет изрыгать ошибку NotCFI для каждого божьего блока выборки. Каждый такой редирект отбрасывает текущую выборку в утиль и приказывает начать все заново с последовательного PC. В наихудшем сценарии фронтенд переваривает лишь один блок выборки в обмен на один штраф от редиректа — примерно 4–5 тактов — низвергая эффективную пропускную способность выборки в 4–5 раз.

Эта клиническая патология редка на практике (для её воплощения требуются систематические коллизии в таблицах предсказателя), но она блестяще иллюстрирует мысль: точность предсказателя влияет не только на высокую производительность бэкенда, но и на банальную пропускную способность самого фронтенда.

> *Глава 8a (раздел 8a.6) раскрывает RTL-потроха модуля `PredChecker` и его логику классификации ошибок.*

## 8.8 Некешируемая выборка инструкций и MMIO

### 8.8.1 Почему нормальный путь через кэш рушится при встрече с MMIO

Регионы 메모ри-мэппированного ввода-вывода (MMIO) обладают фундаментально иной семантикой по сравнению с обыденной памятью:

- **Побочные эффекты (Side effects)**: Чтение адреса MMIO может спровоцировать физические действия аппаратуры (очистку флага прерывания, сдвиг указателя FIFO). Спекулятивные прочтения — которые подсистема кэша может самовольно инициировать задолго до финального коммита — здесь строго под запретом: они способны вызвать необратимые изменения на ложном пути.
- **Некэшируемость**: Данные MMIO нельзя помещать в кэш, так как состояние устройства способно измениться между двумя обращениями. Кэш инструкций, по своей упрямой природе, всегда кэширует.
- **Очередность**: Чтение из MMIO обязано происходить в строгом программном порядке по отношению к предшествующим закоммиченным инструкциям. Спекулятивный out-of-order фронтенд в своем хаотичном рвении непременно бы нарушил этот хрупкий порядок.

Эти жесткие ограничения означают, что всякий раз, когда блок защиты физической памяти (PMP) или атрибуты таблиц страниц клеймят адрес выборки как некэшируемый или MMIO, IFU лишается права использовать свой привычный, широкий тракт через кэш.

### 8.8.2 Сериализованный путь некэшируемой памяти

Решение — выделенный боковой путь, наделенный строгим контролем очередности:

```text
  Нормальный путь:      Некэшируемый путь:
  FTQ ─> ICache ─> IFU  FTQ ─> IFU ─> Uncache FSM ─> Шина памяти
  (спекулятивный,        (сериализованный, одна инструкция за
   конвейерный,           раз, кротко ждет коммита перед
   высокоскоростной)      отправкой запроса)
```

Некэшируемый путь обрабатывает **строго по одной инструкции за раз**. Он повинуется меланхоличной конечной машине состояний (FSM):

1. **Ожидание очереди**: Если выборка легла на алтарь MMIO, жди, пока все до единой предшествующие инструкции не совершат свой коммит. Это гарантирует отсутствие спекулятивных побочных эффектов.
2. **Отправка запроса**: Выпусти одиночный запрос на выборку инструкции в шину памяти.
3. **Получение ответа**: Дождись возвращения единственного слова инструкции от самого устройства.
4. **Внедрение и редирект**: Помести эту одинокую инструкцию в буфер инструкций и соверши редирект фронтенда на следующий, строго последовательный адрес PC для новой выборки.

Это драматически медленнее обычного пути — одна инструкция за полный круговой вояж до шины памяти вместо потенциальных 16+ инструкций за один такт. Однако выборка инструкций из MMIO — явление экстраординарное (свойственное лишь ранней загрузке или прямому исполнению прошивки устройства), так что такая плата за пропускную способность признана приемлемой.

### 8.8.3 Проблема очередности в деталях

Ради чего выборки MMIO обрекают себя на ожидание коммита? Возьмем такой сценарий:

1. Предсказатель гадает, что следующая выборка ждет нас по адресу MMIO 0xF000_0000.
2. IFU выпускает запрос чтения MMIO. Устройство возвращает данные инструкции и необратимо сдвигает свое внутреннее состояние.
3. Бэкенд с опозданием прозревает, что предсказание было ложным — выборка должна была уйти по совершенно иному руслу.
4. Конвейер сбрасывается (flush), но изменение состояния устройства из шага 2 **уже невозможно повернуть вспять**.

Ожидая, пока все предыдущие инструкции не совершат коммит, IFU дает железобетонную гарантию: запрос MMIO отправляется лишь тогда, когда он стал архитектурно неизбежен. Цена — задержка (latency); награда — непоколебимая корректность.

### 8.8.4 Сшивание MMIO инструкций на границе страниц

Сериализованный путь таит в себе еще одну извращенную сложность: 32-битная инструкция способна раскорячиться на границе страниц, оставив первые два байта на одной странице MMIO, а вторые — на другой. Поскольку некэшируемые выборки оперируют гранулярностью единичных транзакций шины (обычно выровненных по 4 байта), первая транзакция возвращает лишь первую 16-битную плоть инструкции — шина не смеет пересекать границу страницы за один запрос.

IFU вынужден распознавать этот надлом и выпускать **две** транзакции:

```text
  Страница A (MMIO): ... [первая половина 32b на смещении 0xFFE]
  Страница B (MMIO): [вторая половина на смещении 0x000] ...

  Транзакция 1: чтение Страницы A → дает 16-битную половину (неполную)
  Транзакция 2: чтение Страницы B → дает вторую 16-битную половину
  Сборка: полная 32-битная инстр. = Cat(половина_из_B, половина_из_A)
```

Машина состояний Uncache FSM сигнализирует "неполно" при первом ответе. IFU бережно прячет первые 16 бит, выпускает вторую выборку для следующей страницы, и наконец, подобно демиургу, лепит из двух половин полноценную 32-битную инструкцию. Лишь после этого обряда инструкция вводится в буфер.

Этот сбой на стыке страниц крайне редок — он требует жуткого сочетания MMIO-региона, исполняемого кода *и* 32-битной инструкции, случайно угодившей точь-в-точь на границу, — но его нужно безукоризненно обрабатывать. В противном случае провал сборки породит необоснованное исключение неверной инструкции на абсолютно легальном коде.

### 8.8.5 Сравнение по индустрии: Подходы к некэшируемой выборке

> **Сравнение по индустрии**
>
> - **Серия ARM Cortex-A**: Исповедует схожий подход — некэшируемые выборки минуют I-кэш и процеживаются сериализованно. Архитектура ARM обособляет типы памяти (Device, Normal Non-cacheable), диктующие такое поведение.
>
> - **Ядра Intel x86**: Здесь грань тоньше, ибо типы памяти x86 (UC, WC, WT, WB) управляются через MTRR и PAT-записи. Некэшируемые выборки инструкций фактически сериализуются фронтендом, хотя мельчайшие детали остаются погребены в проприетарных реализациях (implementation-specific).
>
> - **BOOM (Berkeley Out-of-Order Machine)**: Пускает некэшируемые выборки по обособленной тропе "fetch buffer bypass". Подобно Kunminghu, BOOM сериализует выборки MMIO ради сохранения первозданной очередности.
>
> Паттерн универсален: все без исключения высокопроизводительные дизайны изгоняют некэшируемые выборки в медленный, но спасительно упорядоченный боковой путь.

## 8.9 Жизнеописание инструкции: Одиссея одного блока выборки

Давайте проследим за судьбой одного блока выборки — 64-байтного куска инструкций — сквозь весь конвейер IFU. Мы воспользуемся упрощенным IFU со смехотворными 4 стадиями плюс стадией финального подтверждения записи (write-back check).

**Диспозиция:**
- Блок выборки на PC = 0x8000_0100 таит в себе 10 инструкций (микс из 16- и 32-битных).
- Предсказатель переходов вещает: "переход совершен на инструкции 8" (это JAL на смещении в 22 байта).
- Указатель записи IBuffer'а в текущий момент завис над банком 1.
- Никакого переноса полуинструкций из темного прошлого нет.

| Такт | Стадия | Что вершится в этот миг |
| --- | --- | --- |
| T0 | **Принятие запроса** | FTQ подает цель выборки (PC=0x8000_0100, taken на смещении 22). И IFU, и ICache хором рапортуют о готовности. Запрос запечатлен. |
| T1 | **Детекция границ** | ICache изрыгает 64 байта данных. Детектор границ сканирует полуслова с нулевого и обнаруживает начала инструкций на полусловах {0, 1, 3, 4, 6, 7, 9, 10, 11, 13}. Маска предсказания безжалостно обрезает этот список до {0, 1, 3, 4, 6, 7, 9, 10, 11} (ибо полуслово 13 лежит за чертой перехода). Последняя выжившая инструкция — на полуслове 11; она 32-битная и благополучно умещается в блоке. Флаг переноса полуинструкции продолжает мирно спать. |
| T2 | **Уплотнение + выравнивание** | Логика уплотнения сгоняет 9 выживших инструкций в монолитные смежные слоты 0–8. Логика выравнивания вращает этот хоровод по указателю буфера (банк 1), так что инструкция 0 падает в полосу 1, инструкция 1 — во 2-ю, и так далее. Начинается пред-декодирование: каждая сущность получает свой класс (условный переход, прыжок, или не-переход). |
| T3 | **Проверка + расширение + постановка в очередь** | Плоды пред-декодирования поспевают. Инструкция 8 (на 11 полуслове, где и был предсказан переход) воистину оказывается JAL — чекер предсказаний дает добро, подтверждая совпадение цели (PC + immediate). Грехов не выявлено. Сжатые RVC-инструкции разбухают до своих 32-битных ипостасей. Все 9 душ строем входят в IBuffer. |
| T4 | **Подтверждение write-back** | Вторая (завершающая) стадия чекера гарантирует отсутствие надобности в редиректах. FTQ извещается о благополучном завершении миссии данного блока. IFU готов испить из новой чаши запросов. |

**Итоговая задержка (latency):** 4 такта от принятия запроса до вливания в IBuffer, плюс 1 призрачный такт на финальное утверждение write-back'а. В течение тактов T1–T4 IFU волен поглотить следующий блок уже на T1 (чудо конвейеризации), так что темп в устоявшемся режиме составляет один жирный блок выборки за каждый оборот часов (такт).

А теперь вообразите: что если бы инструкция 8 на самом деле оказалась `c.addi` (а не переходом)? Инспектор (чекер) на такте T3 завопил бы об ошибке NotCFI, вычеркнул бы инструкцию 8 из списка на запись (действие стадии 1), а на такте T4 извергнул бы редирект, указывающий на последовательный PC сразу после инструкции 7. FTQ отмотала бы свое время вспять, и новая выборка началась бы с исправленного адреса. Конвейер потерял бы какие-то смешные 4 такта (глубина самого IFU) — вместо 15-20 тягучих тактов, ушедших бы на мучительное осознание этой же ошибки в бэкенде.

## 8.10 Иерархия приоритета сбросов: Укрощение конфликтующих коррекций

### 8.10.1 Проблема многоликого редиректа

Пайплайн (конвейер) IFU держит в полете сразу несколько стадий одновременно. В любую секунду несколько обособленных сущностей могут в унисон возопить о том, что исполняемая работа стала суетой сует и подлежит уничтожению:

- **Бэкенд** натыкается на ветвь ложного предсказания или порождает исключение (голос истины последней инстанции, авторитарный).
- Собственный **чекер IFU** улавливает структурный сбой (авторитет на уровне фронтенда).
- **Медленный слой** предсказателя (BPU) дезавуирует ошибку своего более проворного, но глупого собрата (спекулятивная коррекция).

Эти откровения могут обрушиться в течение одного-единственного такта. IFU сталкивается с дилеммой: чья коррекция правит бал, и как глубоко следует вычистить авгиевы конюшни конвейера?

### 8.10.2 Иерархия абсолютной власти

Проблема решается внедрением абсолютной, бескомпромиссной иерархии приоритетов, где более высокий авторитет беспощадно глушит более слабый:

```text
  Приоритет 1 (Высший):  Редирект от бэкенда
                         (ошибка предсказания, исключение, нарушение очередности памяти)
                         Сброс: ВСЕ стадии (от s0 до s3 + write-back)

  Приоритет 2:           Редирект от инспектора (чекера) IFU
                         (пред-декодирование уличило BPU в структурной ошибке)
                         Сброс: s0, s1, s2 (но НЕ s3, которая уже ушла в очередь)

  Приоритет 3:           Редирект Uncache/MMIO
                         (выборка MMIO завершена, редирект на следующий последовательный PC)
                         Сброс: s0, s1, s2

  Приоритет 4 (Низший):  Самокоррекция BPU от медленного слоя
                         (точный, но медлительный слой BPU вступает в спор со своим быстрым, но слепым двойником)
                         Сброс: только s0, s1 (до того, как ответ ICache успеет прибыть)
```

Фундаментальная мысль: глубина очистки (flush) у каждого источника **строго своя**. Редирект от бэкенда должен выжечь всё каленым железом — он несет абсолютную архитектурную истину, рожденную из плоти реального исполнения, а не из тумана эвристического пред-декодирования. Самокоррекция BPU, напротив, нуждается лишь в отсечении самых ранних стадий, ибо сама эта коррекция остается спекулятивной иллюзией и может быть легко перебита более поздним, суровым редиректом.

### 8.10.3 Почему приоритет — это залог корректности

Вообразим состояние гонки (race condition): в одном такте инспектор IFU распознает ошибку NotCFI на стадии write-back, а бэкенд выявляет ошибку предсказания совершенно *другой* инструкции. Оба жаждут немедленно направить фронтенд к разным спасительным берегам. В мире без приоритетов IFU мог бы поддаться чекеру, а мгновением спустя быть раздавленным бэкендом — или, что еще страшнее, два редиректа переплелись бы в инцестуозной связи, повергнув конвейер в противоречивый хаос.

Строгий приоритет гарантирует безоговорочную победу бэкенда. Желание чекера породить редирект молча давится в зародыше, поскольку истина бэкенда стоит выше в космическом порядке (ведь она исходит из самого акта исполнения, а не из догадок). Состояние гонки испаряется, не успев родиться.

### 8.10.4 Охранная печать "одной и той же записи"

Есть один изощренный сценарий: стадия write-back и текущая стадия конвейера могут прожевывать *одну и ту же* запись FTQ. В этом зловещем случае логика write-back'а, инициирующая редирект, не должна стирать текущую стадию — ибо последняя уже обрабатывает исправленную, истинную версию этой записи. Архитекторы разрешают это противоречие компаратором проверки "same-entry comparator", который накладывает запрет на flush, если индексы FTQ мистическим образом совпадают.

## 8.11 Философия архитектурных жертв (Трейд-оффы)

### 8.11.1 Ранняя проверка IFU супротив единоличной проверки бэкендом

| Аспект бытия | Ранняя проверка IFU | Единоличная проверка Бэкендом |
| --- | --- | --- |
| **Жизнь ложного пути** | Кратка (глубина IFU, ~4 такта) | Долга и мучительна (весь конвейер, ~15–20 тактов) |
| **Сложность IFU** | Высока (пред-декодер + логика чекера) | Ничтожна (тупая перекачка байтов) |
| **Площадь на кристалле**| Больше комбинационной логики во фронтенде | Меньше фронтенда, но впустую жгутся транзисторы бэкенда |
| **Энергия** | Пред-декодирование сжигает джоули | Инструкции-призраки впустую глотают ресурсы декодирования и выпуска (issue) |
| **Отлавливаемые грехи**| Только структурные (NotCFI, JAL target и пр.) | Абсолютно все, включая условные повороты судьбы |

Современные титаны производительности в едином порыве выбирают раннюю проверку, поскольку сбереженная энергия и убереженная пропускная способность от не-совершения ложного пути с лихвой, многократно окупают скромные затраты на логику самого инспектора.

### 8.11.2 Уплотнение в IFU супротив уплотнения ниже по течению

| Аспект бытия | Уплотнение в IFU | Уплотнение на стороне (IBuffer/Decode) |
| --- | --- | --- |
| **Сложность IFU** | Широченные мультиплексоры, тяжелая логика префикс-сумм | Минимальна — тупо бросай дальше разреженные биты |
| **Сложность бэкенда**| Простенькая блочная запись в банки | Вынужден сам уплотнять перед декодом, растягивая задержку |
| **Зрелая пропускная способность**| Высочайшая — IBuffer кушает плотный, сытный поток | Скромная — зияющие дыры съедают ширину записи |
| **Тайминги** | Уплотнение висит прямо на критическом пути IFU | Давление таймингов перекладывается на уставшие плечи Декодера |

Этот конфликт разрешается там, где тайминги скрипят громче всего. Если у IFU есть слабина (например, снисходительный период такта или лишняя стадия в запасе), уплотнение внутри IFU объявляется священным граалем, поскольку оно максимизирует утилизацию всех последующих трактов.

### 8.11.3 Выделенная машина состояний FSM супротив Единого пути для Uncache

| Аспект бытия | Выделенная машина (FSM) | Единый путь кэша/uncache |
| --- | --- | --- |
| **Освященная очередность**| Эксплицитна — FSM железно блюдет порядок коммитов | Вынуждает вплетать проверки очередности в недра конвейера кэша |
| **Ясность замысла** | Идеальное разделение интересов | Меньше модулей, но шизофреническое переключение режимов |
| **Площадь** | Разбухание за счет лишнего состояния FSM и логики управления | Разделяемый путь данных, меньше клонирования |
| **Верификация** | Легко математически доказать изоляцию потоков | Адски сложно убедиться, что ни капли спекулятивного MMIO не просочилось наружу |

Выделенная машина состояний FSM одерживает триумфальную победу на практике, ибо корректность MMIO является фундаментом самой жизни системы, а доказывать эту святость на запутанном объединенном пути — занятие для безумцев.

## 8.12 IFU в Великом Замысле Конвейера

### 8.12.1 Чем IFU питается

У IFU есть два верховных кормильца (поставщика):

- **FTQ** (Глава 6): поставляет эфемерные цели выборки — изначальный PC, предсказанное смещение совершенного перехода (taken) и учетный индекс самой записи.
- **ICache** (Глава 7): сгружает суровую материю — сырые байты инструкций, обильно сдобренные метаданными (физические адреса, флаги исключений, атрибуты типов памяти: кэшируемая или MMIO-монолит).

Чтобы IFU соизволил принять новый блок выборки, оба поставщика обязаны явиться одновременно. Запнется любой из них — IFU замрет в ожидании.

### 8.12.2 Что IFU порождает

У IFU есть лишь один главный потребитель (выходной слив):

- **IBuffer** (Глава 9): принимает плотный вектор уплотненных, выровненных, растолстевших (расширенных RVC) инструкций. Каждое создание несет на спине свой собственный крест: PC, класс пред-декодирования, флаг валидности и тяжкие метки исключений.

IFU также генерирует вторичный росток обратно к корням (к FTQ):

- **Редирект** (при обнаружении лжи предсказания): спасительный сигнал, заставляющий FTQ перемотать стрелки своих указателей назад и начать выборку с чистого, обновленного адреса.

### 8.12.3 Распространение скверны застоя (Stall Propagation)

```text
  IBuffer переполнен ──> IFU задыхается (stalls) ──> ICache душится ──> FTQ буксует
  (обратное давление)                                (через backpressure)   │
                                                                            │
  FTQ пустеет ─────────────────────────────────────> IFU голодает           │
                                                                            v
  ICache промахивается ────────────────> IFU чахнет в ожи- ──> FTQ не       BPU может
  (cache miss)                           дании данных          сдвигается   продолжать
                                                                            пророчествовать
                                                                            (runahead)
```

IFU — это игольное ушко фронтенда: единственный мыслимый путь трансляции сырых кэшированных байтов в осмысленные инструкции. Когда IFU давится (stalls), и кэш, и FTQ мгновенно ощущают удушье. Когда IFU изнывает от голода (нет запросов от FTQ или байтов от кэша), бэкенд высыхает без инструкций и впадает в оцепенение.

Единственное мистическое исключение из этого мертвенного сцепления — дар предвидения FTQ на опережение (runahead, Глава 6, Раздел 6.4): даже пока IFU парализован промахом кэша, воспаленный мозг BPU способен продолжать плести предсказания и набивать FTQ целями, так что в момент разрешения промаха наготове будет уже целая россыпь маршрутов.

## Ключевое послевкусие

- IFU перекидывает мост между суровыми кэшированными байтами и структурированным потоком мыслей (инструкций), которого так алчет бэкенд. Без него переменная ширина кодирования, разорванные границами блоков инструкции и ошибки предсказаний стерли бы стадию декодирования в порошок.
- Обнаружение границ воскрешает начала инструкций из хаоса смешанного 16/32-битного кодирования. Спекулятивно-параллельные вычисления разрубают узел последовательной цепи переносов в угоду безжалостным таймингам. Состояние межблочного переноса врачует рваные края полуинструкций, включая тонкую алхимию межстраничных исключений.
- Индивидуальные PC пересобираются из общих старших битов и узких, специфичных для каждого слота, младших; использование однобитного мультиплексора обхода переполнения избавляет кристалл от полновесных сумматоров на каждый слот.
- Уплотнение и выравнивание спрессовывают редкий пунктир валидных инструкций в плотные ударные волны, выжимая все соки из нижележащей пропускной способности записи.
- Ранняя инспекция предсказаний ловит структурную ересь в предсказателе (NotCFI, промахи по цели) еще на стадии фронтенда, аннулируя разрушительный штраф полноценного путешествия ложного пути через бэкенд.
- Борьба множества источников редиректа (бэкенд, чекер IFU, самонаблюдение BPU) гасится строгой, тоталитарной иерархией приоритетов, которая решает, не только кто прав, но и насколько глубоко в тело конвейера погрузится скальпель очистки (flush).
- Некэшируемые выборки MMIO изолируются в медленную, ритуально сериализованную боковую тропу с эксплицитным следованием порядку коммитов; там же проводятся церемонии двойной транзакции-сборки для MMIO-инструкций, распятых на границах страниц.

5. **Продвинутый**: Если блок выборки набит исключительно 16-битными (сжатыми) инструкциями, а предсказатель произносит: "переход на последнем полуслове", сколько валидных инструкций родится из чрева IFU? Каков будет коэффициент уплотнения (доля валидных слотов ко всем)?

8. **Элитарный**: Трюк с пересборкой PC опирается на точку отсечения, кромсающую адрес. Если бы мы занизили эту точку (скажем, до бита 4), что сталось бы с объемом хранения каждого слота и частотой переполнений? А если завысили бы её (до бита 20)?
